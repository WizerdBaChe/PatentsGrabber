# Stage 1 深度回顧 — 追溯矩陣與儀器體檢

- 日期：2026-08-27 · 對象：`main` @ `0cc20b1`（Stage 1 全部併入後）
- 這份文件不新增需求、不改任何行為。它回答兩個問題：
  **(A) 每一條規則／需求，今天由誰守著？** **(B) 那些守門員本身可信嗎？**
- 讀法：表格裡的「證據等級」是全文的重點欄位。
  - **可重跑** = 有一支現在就能執行的檢查會失敗
  - **一次性** = 當時量過、寫進紀錄，但沒有東西會在它壞掉時叫
  - **無** = 只有程式碼本身
- 產出的建議集中在 §4，且刻意很短。不是每個「無」都值得補。

## 0. 方法與可翻盤條件

**怎麼查的**：對 `tools/*.py`、`tests/`、`src/patentsgrabber/` 逐一比對 CIM §6 的 BR-1…BR-8、
`docs/05` §4 的 R-1…R-10、§2 的 F-1…F-20，記錄每條規則的實作位置與斷言位置。
所有 gate 於同日在乾淨樹上重跑過（結果見 `docs/05` §5.5）。

**這份回顧的成立條件**：它描述的是 `0cc20b1` 這一份程式碼。任何一次改動 gate 或
擷取器都會使 §1–§2 的表格部分失效——**推翻方式**：重跑一次同樣的比對，成本約 20 分鐘。

**一個要先更正的印象**：上一輪對話裡我說「`R-*` 在 gate 與原始碼中一次都沒出現」——
字面為真（那些 ID 確實沒被寫進程式），但由此推論「閱讀需求全靠人眼」是過頭了。
逐條比對後，**R-1 / R-4 / R-5 / R-6 其實有機器守門**，只是沒掛 ID。真正沒人守的是
瀏覽器那一層（R-2 / R-7 / R-8 / R-9 / R-10）。下面的表格是更正後的版本。

## 2. 閱讀需求 R-1…R-10

| ID | 誰在守 | 證據等級 |
|---|---|---|
| **R-1** 描述分塊、段號在側欄 | `check_reading.py`：`blocks == 0` 即失敗、空塊即失敗、覆蓋率須落在 [0.98, 1.02] | **可重跑**（20 份文件） |
| **R-2** 排版可調且持久化 | 無。`localStorage` 的寫入與回讀沒有任何自動檢查 | **一次性** |
| **R-3** 章節大綱與跳轉 | 半條：`check_reading.py` **計數** headings 但 **不斷言**（`analyse()` 有 `headings` 欄，`verdict()` 不看它）。跳轉行為無檢查 | **無斷言（有可讀數字）** |
| **R-4** `FIG. n` 可點 | `check_reading.py` 正反對照：三份應有 figref 的文件 > 0、三份不應有的 = 0。點擊行為本身無檢查 | **可重跑（抽取半邊）** |
| **R-5** 請求項樹 | `check_reading.py` 的 claim coverage，且該指標對「舊解析器」重播過（0.282 會被擋下） | **可重跑，且已校準** |
| **R-6** 純文字可複製 | 覆蓋率指標正是這條：結構化後的字數必須貼齊原始扁平文字 | **可重跑** |
| **R-7** 元件編號高亮 | 無。UI 端 `#c-numeral`、`READ_DEFAULTS.numerals=false`；抽取端 `figure-callout` | **無** |
| **R-8** 不得靜默等待 | 無。§5.2 記錄了觀察到的階段字串與計時器 | **一次性** |
| **R-9** 版面隨視窗 | 無。§5.2 的 30.0 % / 34.0 % 與各面板像素數 | **一次性** |
| **R-10** 字級與行寬隨螢幕 | 無。§5.2 的 18px/76ch、17px/72ch 與 pin 行為 | **一次性** |

**結論**：機器守得住的是「**文字有沒有被弄丟、結構有沒有被抽出來**」；守不住的是「**讀起來對不對**」。
這個分界其實合理——後者本來就需要人眼——但 R-9／R-10 是例外：它們是**可量測的數字**
（欄寬、面板寬、有無水平溢位），現在卻被當成觀感在處理。§4 的建議只針對這個例外。

## 3. 儀器體檢：守門員本身可信嗎

### 3.1 做得對的地方（要保留，不要在重構時弄掉）

| 儀器紀律 | 在哪 |
|---|---|
| **壞輸入必須被擋下**（負向校準） | `check_reading.py`：拆掉段落標記的頁面必須失敗，且會明說「checker 沒在量任何東西」 |
| **指標對它要抓的缺陷校準過** | claim coverage 對舊解析器重播 → 0.282 擋下、1.000 放行；巢狀樣本在新舊兩版都 1.000（不會亂叫） |
| **查詢建構的校準** | `check_search.py` §1：手工兩子句查詢必須被 matcher 拒絕，證明這個檢查有能力失敗 |
| **系統性故障偵測** | `check_reading.py`：某個指標在**所有**文件上都是 0 → 印 `SYSTEMATIC FAILURE`，把「全體一致」視為儀器故障而非結論 |
| **正反雙向對照** | figref 三正三負；EN/DE/FR 附屬項九案雙向；零結果是答案不是錯誤 |
| **紅燈轉為斷言而非刪除** | `verify_ops.py` §4：US 全文不可用從「失敗」改寫成「預期不可用」，OPS 哪天開放反而會 FAIL——這是**設計成警報的紅燈** |

這一組是 Stage 1 真正的資產。下面的缺口都比不上它們重要。

### 3.2 盲點（按影響排序）

**I-1 · `check_reading.py` 是回歸測試，不是活的偵測器。**
它讀的是 `var/raw/` 裡 20 份 **存檔 HTML**。若 Google Patents 明天改掉描述標記，
這支檢查 **仍然 20/20 全綠**，因為它比對的是舊檔案。`docs/05` §7 寫著
「The checker is the tripwire」——這句話**只在有人重新抓頁面時成立**。
今天沒有任何東西會重抓。這是本次回顧最重要的一條：**專案最活躍的外部依賴，
偵測器是靜態的。**

**I-2 · schema 常數的規則只是一句叮嚀，沒有機制。**
`CLAUDE.md` 要求「改擷取器就在同一次 commit 動 `READING_SCHEMA` / `OPS_CARD_SCHEMA`」，
而這條規則是**踩過兩次**才寫下的。再讀（`service.py:555`、`:529`）時的重新推導機制是好的、
自動的；問題只在「忘記加一」——而防止忘記的目前手段是記憶。
這正是全域規則說的反例：規則應寫成**資產的性質**，不是對路徑的叮嚀。

**I-3 · 配額只被印出來，沒有被斷言。**
BR-6 的兩個實質承諾——「頁面位元組隨看隨取」「重讀不花配額」——都沒有檢查。
`Usage.summary()` 是給人看的字串。若某次重構讓建卡順手預抓縮圖，
所有 gate 仍然全綠，只有 EPO 的週計數器會安靜地爬。

**I-4 · 沒有一鍵執行，也沒有 CI。**
五支 gate 各自獨立執行，其中三支要網路與配額。實務上「守門」等於「我記得要跑」。
本機單人、無 remote，CI 不適用；但一支聚合器（先跑離線的，再問要不要跑耗配額的）
是成立的。

**I-5 · 分數不可跨時間比較。**
`check_reading` 的「20/20」分母是 `var/raw/` 的檔案數，會隨取樣增加而變；
`check_search` 的「20/20」是檢查項數。兩個 20 意義不同，紀錄裡並排時看起來像同一種東西。

**I-6 · 兩支 gate 沒有校準案。**
`smoke_service.py` 與 `tests/test_ops_number_formats.py` 全綠，但沒有任何
「已知為真應被擋下」的反例證明它們有能力失敗。相較 §3.1 的紀律，這兩支是漏網的。

## 4. 建議（只有四條，按投報比排序）

> 前提：Stage 1 的核心需求已滿足，這裡沒有一條是「功能不足」。
> 全部不做也不會讓現有功能出錯——它們買的是「壞掉時會被發現」。

**建議 1 · 新鮮度探針（對應 I-1）** — 值得做
一支小工具，重抓 `var/raw/` 裡 2–3 件已存檔文件，與存檔版比對**結構統計量**
（blocks／claims／figrefs 落在容差內），不比對逐字內容。有網路才跑，不耗 OPS 配額
（Google Patents 不計 OPS 額度）。這把 §7 那句「checker is the tripwire」變成真的。

**建議 2 · 擷取器指紋（對應 I-2）** — 值得做
在 `tests/` 加一條：把擷取函式的原始碼雜湊記為常數，改動而未同時提高
`READING_SCHEMA` / `OPS_CARD_SCHEMA` 即失敗。把記憶型叮嚀轉成資產性質。
成本一支小測試；代價是每次正當改動要更新雜湊——這正是它要製造的那個停頓。

**建議 3 · 版面自檢（對應 R-9／R-10）** — 值得做，但要挑範圍
只斷言三件可量測的事：欄寬不超過設定的 measure、頁面無水平溢位、
自動配對（px/ch）會隨視窗寬度改變。既有的 `tools/shoot.py` 已經在驅動無頭 Chrome，
不需要新裝 Playwright。**不要**去斷言像素級外觀——那仍然是人眼的事。

**建議 4 · 一鍵 gate 聚合器（對應 I-4／I-5）** — 順手做
先跑離線的三支，再明示「以下會用到 OPS 配額」後跑其餘兩支，最後一併印分母來源。

**不建議做**：BR-7 的 URL pin（結構上已安全，加測試是為做而做）；
R-7 的自動檢查（預設關閉的加值功能）；F-9/F-10 的上限監看（改動風險低、
影響僅止於一個字面數字，人工重測即可）；I-6 的補校準（這兩支 gate 的斷言
本身簡單直接，加人工反例的收益低於維護成本）。

## 5. review-when（本文件自身）

- `var/raw/` 的取樣份數改變 → §2 的「20 份」與 §3.2 I-5 需重讀。
- 任何一支 `tools/check_*.py` 改動 → §1/§2 的「誰在守」欄位失效，需重跑比對。
- 建議 1–4 任一條落地 → 對應列的證據等級改變，回來改這張表，不要另開新檔。
- Stage 2 開工 → 本文件的「已滿足」前提僅涵蓋 Stage 1 範圍。
